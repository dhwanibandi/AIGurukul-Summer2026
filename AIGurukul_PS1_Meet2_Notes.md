## 3. Paper Discussion: Neuro-Symbolic Verification of Instruction-Following (NSVIF)

### 3.1 Paper Introduction

- Shared by: **Ojas Marathe** (who summarized the paper)
- Two of the paper's authors were personally met by Anupam at **UIUC (University of Illinois Urbana-Champaign)** the previous month.

### 3.2 Core Problem the Paper Addresses

> *"When you ask an LLM to write a 500-word essay in a formal tone to a professor, how do you verify that it actually followed all the rules?"*

LLMs frequently **violate user-defined constraints** (called **violations** in the paper), such as:
- Exceeding word count limits
- Using incorrect tone
- Including or excluding specific words/topics

The NSVIF paper proposes a **three-agent architecture** to solve this verification problem systematically.

---

### 3.3 NSVIF Architecture: Three-Agent System

```
User Instruction
      │
      ▼
┌─────────────┐
│  Agent 1:   │  ──► Breaks instruction into formal logical constraints
│  Formulation│       (e.g., tone = formal, word_count ≤ 500, topic = education)
└─────────────┘
      │
      ▼
┌─────────────┐
│  Agent 2:   │  ──► Classifies each constraint as:
│  Checking   │       • Logical (binary, rule-based)
└─────────────┘       • Semantic (language-understanding required)
      │
      ├──── Logical ──► Simple Python program (True/False check)
      │
      └── Semantic ──► LLM-as-Judge (uses GPT-4o as evaluator)
                │
                ▼
       ┌─────────────┐
       │  Agent 3:   │  ──► Z3 Solver (from Microsoft Research)
       │   Solver    │       Checks satisfiability of first-order logic clauses
       └─────────────┘
```

#### Agent 1 – Formulation Agent
- Decomposes natural language instructions into **formal logical constraints**.
- Example: "Write a formal essay under 500 words" → `{tone: formal, word_count ≤ 500}`

#### Agent 2 – Checking Agent
- Classifies each constraint into one of two types:

  | Type | Description | How Verified |
  |---|---|---|
  | **Logical** | Definite true/false answers (e.g., word count) | Simple Python script |
  | **Semantic** | Requires language understanding (e.g., tone, topic relevance) | LLM-as-a-Judge (GPT-4o) |

#### Agent 3 – Solver Agent
- Uses the **Z3 Solver** (Microsoft Research) to verify **satisfiability** of the formal logic expressions generated by Agent 1.
- Z3 checks Boolean and first-order logic satisfiability problems.

---

### 3.4 Benchmark Results & Key Observations

- NSVIF **significantly outperforms all baselines** on standard benchmarks.
- **One exception:** It performs *worse* when using **GPT-4o mini** as the LLM judge.

#### Why GPT-4o Mini Fails:
- It **misclassifies constraints** — e.g., it treats a semantic constraint like "does the essay discuss education?" as a *logical* one, and simply checks if the word "education" appears in the text.
- This causes cascading failures: if Agent 2 (Checking) is wrong, Agent 3 (Solver) receives incorrect inputs → verification fails → Agent 1 cannot self-correct.

> **Key Insight:** The quality of the LLM used as a judge is critical. A small/weak model breaks the entire pipeline.

---

### 3.5 LLM-as-a-Judge — Concept Clarification

Anupam introduced and clarified the **LLM-as-a-Judge** pattern using one of his own published papers (co-authored with an IIT Madras student):

- **Standard use of LLM:** Generate text output.
- **LLM-as-a-Judge:** Use a language model to *evaluate the quality* of another model's output.
- Example prompt: *"You are an impartial judge. Evaluate the quality of these two responses from Assistant A and Assistant B, given the following context…"*
- In one experiment, using **GPT-4.1 as a judge** with NSVIF improved performance from **69.1% → 94.8%**.

---

### 3.6 Encoder vs. Decoder Architecture — Clarification

During discussion on why smaller models fail, Anupam clarified the role of model architecture:

| Architecture | Good At | Example Use Case in NSVIF |
|---|---|---|
| **Encoder-based** (e.g., BERT) | Natural Language Understanding (NLU) — classification, semantic tasks | **Checking Agent** (classifying constraints) |
| **Decoder-based** (e.g., GPT) | Language generation — token prediction | **Formulation Agent** (generating code/constraints) |

> **Insight:** The checking agent is essentially a **binary classification problem** — so an encoder-based model fine-tuned for that specific task would be far more effective than a general-purpose decoder LLM.

---

### 3.7 Open Research Direction: Fine-tuned Small Language Models

Anupam proposed an improvement over the paper's current approach:

**Current limitation:** Both agents use large, general-purpose LLMs (GPT-4o).

**Proposed approach:**
- Replace with **specialized Small Language Models (SLMs)**:
  - **Agent 1 (Formulation):** Fine-tune a decoder-based SLM on constraint formulation tasks.
  - **Agent 2 (Checking):** Fine-tune an encoder-based SLM on semantic/logical classification tasks.
- This results in a system that is:
  - More **cost-effective** (lower inference cost)
  - Less **compute and token hungry**
  - Potentially **more accurate** on narrow, well-defined tasks

> **Analogy by Anupam:** *"You can't make someone a doctor AND a painter AND a professor. If you narrow the task, you narrow the required knowledge — and a small model fine-tuned on that task can outperform a large general model."*

---

### 3.8 Questions & Clarifications from Participants

**Q (Bhavya Shah):** For semantic constraints, are different LLMs used for each constraint type, or one general model?
> **A:** Currently, one general-purpose LLM (GPT-4o) handles all semantic constraints. The improvement would be to replace this with task-specific fine-tuned models.

**Q (Aayush Aggarwal):** If LLMs can't be trusted to follow instructions, how can we trust another LLM to verify? Doesn't that defeat the purpose?
> **A:** The solution is to use a **specialized, fine-tuned** model for verification — not a general-purpose one. Since this model is trained *specifically* for the verification task (classification), it is more reliable for that narrow problem. The generator and verifier work in tandem.

## 4. Problem Statement 1 (PS1) — Engineering Drawing Verification

---

### 4.2 Problem Definition

**Goal:** Build a two-agent agentic system that:
1. **Agent 1 (A1):** Generates Python code (using a DXF library) to create a 2D engineering drawing (`.dxf`/`.dwg` file) of a house plot layout.
2. **Agent 2 (A2):** Verifies the generated code against a set of constraints (both logical and semantic), using a solver (Z3), and provides feedback to A1.

```
User Input (plot dimensions + constraints)
            │
            ▼
     ┌──────────────┐
     │   Agent 1    │  ──► Generates Python code (DXF file of plot layout)
     │ (Generator)  │
     └──────────────┘
            │
            ▼  (code output)
     ┌──────────────┐
     │   Agent 2    │  ──► Verifies constraints are met
     │  (Verifier)  │       Uses Z3 Solver for satisfiability
     └──────────────┘
            │
     ┌──────┴──────┐
     │             │
  PASS           FAIL
     │             │
     ▼             ▼
 Final DXF    Feedback → back to A1 (loop)
```

---

### 4.3 Technical Stack

| Component | Tool/Technology |
|---|---|
| 2D Drawing File Format | `.dxf` (DXF Python library — `ezdxf`) |
| Code Generator | LLM (via API — GPT, Claude, Gemini, etc.) |
| Constraint Solver | Z3 Solver (Microsoft Research) |
| Constraint Source | Seattle Building Code (SBC) — well-documented, publicly available |

> **Note:** `ezdxf` is a Python package that can programmatically create DXF/DWG engineering drawing files.

---

### 4.4 Concrete Problem Specification (Plot Layout)

Anupam sketched a specific problem on screen (participants were asked to take a screenshot):

**Plot Dimensions (Land Parcel):**

```
         North
           │
  ─────────────────────
  │                   │ 75 ft
  │    [Tree]         │
  │  (2.5ft x 2ft)    │
  │   at center       │ 80 ft
  │                   │
  ─────────────────────
         South

  Width (East-West): 50 ft
  Other measurements: 10 ft, 5 ft, 40 ft, 20 ft offsets
```

**Key Constraints:**
- The **tree cannot be cut** (Seattle regulation: ~$50,000 fine + 6 months permit).
- **Offsets** must follow **Seattle Building Code (SBC)**.
- Maximize **area coverage** (land utilization).
- The layout must include **only the outer periphery** of the house.
- A **single entry point** (main door + parking) must be on the same side — per SBC fire safety norms.

**Agent 1's Task:**
- Generate Python (DXF) code to draw the outer periphery of a house on this plot, following all constraints.

**Agent 2's Task:**
- Verify the generated code against SBC constraints and geometric rules.
- If constraints are violated, output specific feedback: *"Out of 3 constraints, you missed X — fix and regenerate."*
